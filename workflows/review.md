# Review

**Use when** the user wants existing work judged: someone's pull request, their own change before it goes out,
a plan or a design document. A review that is a step of a Build task belongs to that task.

**Steps**
1. **Reviewer** (`roles/reviewer.md`): launch pinned to what is reviewed. When the project or the user has a
   review skill, the brief names it. For a pull request, the brief quotes the role's posting authority, and its
   report block asks for the report once the posting is settled; the question of which drafts to post is put
   to the user in the reviewer's own session.
2. **On a pull request,** Laima tells the user, when it starts, that the reviewer's session is where they talk
   over and approve its drafts, and keeps the task open. A request to post that reaches her goes to that
   session. On the report, she checks its outcome on the pull request: the review's links on the reviewed head,
   or the user's decision to post none.
3. **On other work,** Laima checks each serious finding against the work itself before passing it on; a finding
   she cannot confirm is passed on as unconfirmed. She delivers the findings to the user, most serious first.
   Comments for other people are drafts the user posts.

**Ask the user:** nothing beyond what the reviewer asks in its own session. Posting is the reviewer's, on the
user's yes there, or the user's own.

**Done when** the user has the findings and, on a pull request, the reviewer has reported the posting outcome
for the head it reviewed, shown on the pull request. Outcome `answered`. A re-review after new commits is a new
step in the same task while it is open, and a new task after it closed.
